# Test Plan – Project 04: End-to-End Test Automation Framework

| Item | Value |
|---|---|
| Application under test | SauceDemo – https://www.saucedemo.com (public practice site by Sauce Labs, intended for UI automation practice) |
| Test type | Automated functional E2E regression (UI) |
| Framework | Java 21, Selenium 4.50, TestNG 7.11, AssertJ, Allure 2.35, Maven wrapper |
| Author / date | QA portfolio – November 2026 |

## 1. Objectives
1. Provide a maintainable, reusable automation framework (POM, components, fixtures, config, parallelism, evidence on failure, readable reports).
2. Automate the critical shopping journeys: login, product listing & sorting, product details, cart, checkout, logout.
3. Detect and document defects with reproducible automated evidence.

## 2. Scope
**In scope:** login (positive, negative, locked account, access control), inventory listing and sorting, product details,
cart add/remove/persistence, checkout step 1 validation, overview price maths (item total + 8% tax = total), order
confirmation, burger menu, logout/session end.

**Out of scope:** payment processing (none exists), performance (project 05), security scanning (project 06),
accessibility (project 07), cross-browser matrix (project 02 – reuses this framework), the external "About" site.

## 3. Assumptions & constraints
* SauceDemo stores state client-side (cookie + localStorage); a fresh browser per test gives isolation.
* Demo users are documented on the site itself: `standard_user`, `locked_out_user`, `problem_user`,
  `performance_glitch_user`, `error_user`, `visual_user` (password `secret_sauce`). These are public demo accounts.
* `problem_user`, `error_user`, `visual_user` intentionally contain defects; those tests are tagged `known-defect`.
* No real personal data: checkout names/postcodes are generated by Datafaker.

## 4. Test environment
| Component | Version |
|---|---|
| OS (local) | macOS 26 (Darwin 25.6), Apple Silicon |
| JDK | OpenJDK 26.0.1 (bytecode level 21) |
| Browser | Google Chrome (stable, headless `--headless=new`), chromedriver via Selenium Manager |
| CI | GitHub Actions `ubuntu-latest`, Chrome headless, `-Denv=ci` (retry 1) |

## 5. Test design techniques
* **Equivalence partitioning / boundary**: empty vs. invalid vs. valid credentials; empty required checkout fields.
* **Data-driven**: TestNG `@DataProvider` for users, invalid credentials, products, missing fields.
* **State transition**: product button Add ↔ Remove, cart badge counts, logged-in → logged-out.
* **Calculation oracle**: item total = Σ prices; tax = 8% rounded half-up; total = item total + tax.
* **Error guessing**: SQL-injection-like strings, whitespace/case variants of username, Back after logout.

## 6. Entry criteria
* SauceDemo reachable (HTTP 200) and login page renders.
* `qa-core` built; Chrome installed; test code compiles.

## 7. Exit criteria
* 100% of non-`known-defect` regression tests pass (no open Critical/Blocker regressions in the standard flow).
* Every failing `known-defect` test is linked to a defect report with evidence.
* Allure + TestNG reports generated and archived.

## 8. Suspension / resumption
Suspend if the site is down or returns 5xx for > 15 min, or if a Blocker in login prevents all journeys. Resume once the
site responds and a smoke run (`testng-smoke.xml`) is green.

## 9. Risks
| Risk | Mitigation |
|---|---|
| Third-party site changes UI/content | `data-test` locators, tolerant assertions where content is expected to evolve |
| Flaky timing (animations, slow users) | explicit waits only, retry once in CI with flaky log |
| Parallel interference | ThreadLocal driver, no shared state |

## 10. Deliverables
Framework code, suites (`testng.xml`, `testng-smoke.xml`, `testng-known-defects.xml`), Allure/TestNG reports,
[defects.md](defects.md), [execution-summary.md](execution-summary.md), [evidence](evidence/).
